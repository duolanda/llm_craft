# LLMCraft：LLM 战略能力失败问题说明（供外部专家评审）

> 日期：2026-07-26  
> 目的：向不了解 LLMCraft、无法查看源代码的专家完整说明系统、实验事实、已经尝试过的改动和仍未解决的问题。本文尽量把事实、观察和假设分开；我们希望专家独立判断，而不是替已有方案背书。

## 1. 一句话问题

LLMCraft 是一个让 LLM 通过 tool calling 实时控制 RTS 军队的实验项目。在五局 `deepseek-v4-flash` 对内置 `random CPU` 的 benchmark 中，LLM 五局全败，而且五局都从未对敌方 HQ 造成任何伤害。LLM 能采矿、造建筑、生产单位、读取战场，也会频繁调用工具，但长期表现更像逐个执行局部任务的操作员，而不是围绕胜利条件组织经济、生产和军事行动的指挥者。

我们先后尝试过：强化通用 plan、降低 plan 注册难度、增加战略提示，以及把常用战略包装成普通参数工具。最新实验表明，参数化的持续生产工具被模型采用并正确运行，但参数化的全军进攻工具仍完全没有被调用。问题因此不能简单归结为“plan 不会写”或“禁用一个底层工具即可解决”。

## 2. 项目是什么

LLMCraft 是一个确定性模拟的实时战略游戏：

- 服务端：Node.js + TypeScript。
- 模拟以固定 tick 推进，默认每 500ms 一个 tick。
- 两名玩家各自拥有经济、工人、战斗单位和建筑。
- 地图默认是 `144 × 96`。
- 双方 HQ 默认位于 `(14,48)` 和 `(129,48)`。
- 当前没有战争迷雾：AI 的读取工具可以看到全图单位、建筑、资源和地形。
- 单位自动索敌仍受自身视野范围约束，但这不限制 AI 读取敌方全图信息。
- 胜利条件是摧毁敌方所有建筑；只摧毁 HQ 并不会立即获胜。

主要单位：

| 单位 | 作用 |
|---|---|
| `worker` | 采矿和建造 |
| `soldier` | 近战/基础步兵 |
| `rifleman` | 普通远程机枪兵，便宜且对步兵有效 |
| `rocket_soldier` | 反载具和对建筑火力 |
| `light_tank` | 高生命载具 |

主要建筑：

| 建筑 | 作用 |
|---|---|
| `hq` | 初始总部，生产 worker |
| `barracks` | 生产步兵 |
| `war_factory` | 生产 light_tank，需要先完成 barracks |
| `refinery` | worker 的矿物交付点，用于缩短运输路线 |

经济、建造、生产、移动、弹丸、战斗和胜利判断都由服务端逐 tick 结算。工具返回 `ok: true` 只表示命令被接纳，不表示动作已经瞬间完成。

## 3. Agent 与实时模拟如何配合

### 3.1 一个 turn 可以覆盖整局，这是刻意设计，不是已知缺陷

LLMCraft 使用标准 agent tool loop：

1. 模型收到当前游戏摘要和工具定义。
2. 模型可以返回一个或多个 tool calls。
3. 服务端执行工具并把结果返回模型。
4. 模型继续请求工具或结束本次 run。

同一个 turn 内可以连续发生多次模型请求和多轮工具调用，甚至覆盖整场比赛。CLI harness 以及 Claude Code、Codex、Pi 一类 agent harness 也可以在一个用户 turn 内完成长任务。我们明确不把“一个 turn 很长”或“一个 turn 内调用许多工具”本身视为问题，也不希望评审建议仅仅把它机械拆成多个 turn。

游戏 tick 不等待模型：

- 每个 committed tick 都是一次新的决策机会。
- 如果某一方仍有 in-flight 决策，该 tick 只跳过该方的新调度，不会打断其当前 tool loop。
- 另一方不会被慢方阻塞。
- 同一个 LLM turn 中的后续工具调用可以读取更新后的 tick 和战场状态。

因此，“长 turn”并不妨碍模型持续观察和行动。单次模型请求的墙钟延迟仍是一个可测量变量，但它与“必须拆成多个 turn”是两件不同的事。

### 3.2 控制边界

LLM、CLI 和内置 CPU 最终都通过同一个 `GameplayController` 使用相同的观察和动作语义。动作会被提交到单局 `CommandGateway`，只在 tick 边界进入模拟；任何控制器都不能异步直接修改世界状态。

模型当时可用的主要读取工具：

- `get_map_state`：全图单位、建筑、资源和可选格子信息。
- `get_my_state`：经济、建筑、生产队列和可建造/可生产状态。
- `get_my_units`：己方单位及按 role/intent 聚合的 groups。
- `get_army_summary`：双方兵种数量、战斗单位和最大局部兵团摘要。
- `get_active_plans`：已有持续计划及状态。
- `get_recent_events`：近期命令反馈和重要事件。

主要即时动作工具：

- `move_unit(unitIds, x, y)`
- `attack_move_unit(unitIds, x, y, priority?)`
- `attack(unitIds, targetId)`
- `spawn_unit(buildingId, unitType)`
- `build_structure(unitId, buildingType, x?, y?)`
- `start_harvest_loop(unitId, x?, y?)`
- `hold_unit(unitId)`

这些工具可以批量控制单位，没有每 tick 命令额度。批量中的每条 action 独立执行，一条失败不会回滚其他成功动作。

## 4. `random CPU` 实际上做什么

“random”表示它会从当前可行的宏观候选中随机选择，例如采矿、造 worker、造科技建筑、生产步兵、生产坦克或攻击。它不是让每个单位在地图上随机游走。

它还包含稳定的过程规则：

- 没有 worker 时优先补 worker。
- 没有 barracks 时会建 barracks。
- 每轮都会给需要工作的 worker 分配持续采矿。
- 生产步兵时，会依据敌方是否有载具在 rifleman、rocket_soldier 和 soldier 中选择当前可支付单位。
- 选择“attack”后，会遍历战斗单位：有合适目标时直接 attack，否则 attack-move 到敌方基地。
- 当战斗单位达到一个固定集结阈值时，会把尚无攻击命令的单位分到上、中、下三条路线，向敌方基地附近推进。
- HQ 被摧毁后，它会继续寻找并攻击剩余建筑，而不是误以为已经获胜。

因此它的宏观选择含随机性，但执行层拥有持续、机械而一致的 doctrine：采矿、生产、把无任务战斗单位推向敌方建筑。它没有语言理解或复杂推理，却能把已生产战斗力稳定转换为进攻压力。

CPU 没有模型网络请求，因此决策成本远低于 LLM；它在许多样本中会产生数千次工具调用。这个吞吐差异是 benchmark 的实验条件之一，但我们目前观察到的核心失败不仅是动作数量少：LLM 多局完全没有攻击敌方 HQ，并反复把部队停留在己方前沿或处理中场局部事件。

## 5. 五局原始 benchmark

模型均为 `deepseek-v4-flash`，对手均为 `builtin-cpu-random`。五局使用 evaluation Match Record，但 `includeTranscript=false`，所以可以还原工具调用、命令、结果和时序，不能查看模型的自然语言思考或完整消息文本。

| 样本 | LLM 方 | 终局 tick | LLM model requests | LLM tool calls | `orchestrate_plan` | `spawn_unit` | `attack_move_unit` | LLM 首次伤害敌方 HQ | CPU 首次伤害 LLM HQ |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 基线 1 | P1 | 361 | 111 | 153 | 2 | 21 | 7 | 从未 | T244 |
| 基线 2 | P1 | 515 | 186 | 133 | 0 | 27 | 8 | 从未 | T307 |
| 基线 3 | P2 | 635 | 175 | 261 | 2 | 78 | 6 | 从未 | T356 |
| 基线 4 | P1 | 749 | 172 | 202 | 8 | 25 | 0 | 从未 | T185 |
| 基线 5 | P2 | 868 | 265 | 309 | 1 | 58 | 25 | 从未 | T294 |

共同结果：

- LLM 0 胜 5 负，换边也没有改变结果。
- 五局中 LLM 都从未对敌方 HQ 造成伤害。
- LLM 并非没有活动：每局有 133–309 次工具调用、111–265 次模型请求。
- LLM 会采矿、补 worker、建造、生产不同兵种、移动、attack-move，也偶尔注册 plan。
- 但这些行为没有组成可持续的胜利路径。
- CPU 最终都能把进攻推进到 LLM HQ，并在摧毁 HQ 后继续清理其他建筑。

典型表现不是“完全不行动”，而是：频繁读取状态、逐项维护经济、反复生产、把部分单位移动到较近的中场位置、针对眼前单位做局部处置，但没有持续把全军导向敌方建筑。

## 6. 原有通用 plan

原系统向 LLM 暴露 `orchestrate_plan`。它是一个 JSON 工作流 DSL，而不是一个简单战略命令。模型需要填写：

- `unitIds`
- `steps`
- 每个 step 的 `call` 与 `args`
- `global` / `per_unit` scope
- `when` / `until` 条件
- `retry`
- `loop`
- 可选占位符，例如 `$unitId`、`$barracks`

它理论上可以表达跨 tick 的移动、攻击、生产、建造和等待条件，但调用成本显著高于 `spawn_unit(buildingId, unitType)` 或 `attack_move_unit(unitIds, x, y)`。此外，per-unit plan 的单位集合在注册时固定，新生产单位不会天然自动加入原有进攻 plan。

五局基线中，模型分别调用通用 plan 2、0、2、8、1 次。即使调用，也没有形成对敌方 HQ 的伤害。

## 7. 实验 A：强化通用 plan（已经撤回）

我们曾尝试：

- 允许纯 global plan 不提供 `unitIds`，使持续生产更容易表达。
- 改善误把建筑 ID 当 plan owner 时的错误反馈。
- 在 system prompt 中明确要求 plan-first、以兵团和战略目标为单位思考。
- 提醒模型关注 `combat:none` / `combat:hold`，并要求中场集结最终指向敌方建筑。
- 增加计划注册成功率、战斗单位命令覆盖率、闲置率等分析指标。

随后使用 `oc-deepseek-v4-flash` 对 random CPU 跑一局：

- CPU 获胜，346 ticks。
- LLM：22 次模型请求、65 次工具调用。
- `orchestrate_plan`：0 次。
- `spawn_unit`：16 次。
- 成功生产 10 个 rifleman、6 个 worker。
- 只有 1 次 attack。
- LLM 从未伤害敌方建筑。
- 离线指标显示 LLM 战斗单位进攻命令覆盖率约 10%，闲置率约 55.7%；CPU 对应约 97.3% 和 4%。

关键调用链：模型在约 T91 读取 `get_active_plans`，明确看到 `plans: []`；之后仍连续手工生产 8 个 rifleman，没有注册全局生产或进攻 plan。残局看到 `combat / intent:none` 的新兵后，也只给单个单位下了一次 attack。

结论仅限于该样本：强化说明和降低通用 plan 的一部分语法门槛，没有促使模型采用 plan。该实验的代码改动随后全部撤回。

## 8. 实验 B：把常见战略做成普通参数工具（当前工作区实现）

我们撤回实验 A 后，保留内部 Mission 能力，但不再向 LLM 暴露通用 `orchestrate_plan` DSL。CLI 和内部建造流程仍可使用它。

LLM 当前新增三个普通工具。

### 8.1 `maintain_production`

```json
{
  "unitType": "rifleman",
  "targetCount": 10
}
```

服务端负责：

- 自动选择兼容且已完成的生产建筑。
- 等待资源和空闲生产队列。
- 计算存活单位和已排队单位。
- 发生伤亡后继续补到目标数。
- 同一兵种再次调用会更新目标。
- `targetCount=0` 取消该兵种的生产战略。

它不会自动建造缺失的生产建筑；没有合适建筑时状态为 `waiting_for_producer`。

### 8.2 `launch_assault`

```json
{
  "minimumGroupSize": 6,
  "includeFutureUnits": true,
  "targetId": "optional_enemy_building_id"
}
```

服务端负责：

- 等待战斗单位达到最低规模。
- 默认吸纳之后生产的所有战斗单位。
- 省略 targetId 时先向敌方 HQ 进攻，HQ 摧毁后转向其他存活建筑。
- 每个 committed tick 检查新兵和目标状态。
- 给尚未执行当前目标的单位生成 attack 或 attack-move 命令。

当前只允许一个主进攻战略；再次调用会替换它。

### 8.3 `cancel_strategy`

取消某兵种生产、全部生产、主进攻或全部高层战略。

### 8.4 实战结果

使用同一模型 `oc-deepseek-v4-flash` 对 random CPU 跑一局：

- CPU 获胜，819 ticks。
- LLM：52 次模型请求、122 次工具调用。
- `maintain_production`：5 次。
- `launch_assault`：0 次。
- `spawn_unit`：0 次。
- `attack_move_unit`：9 次。
- LLM 从未伤害敌方 HQ。
- CPU 在 T565 首次伤害 LLM HQ，T667 摧毁 HQ，T819 清理完全部建筑。

`maintain_production` 的后台 provenance 证明它实际执行，而不只是注册成功：

- `production_worker:spawn`：17 条成功生产命令。
- `production_rifleman:spawn`：13 条成功生产命令。

模型对生产战略的使用过程包括：

- worker 目标先设为 8，后改为 10。
- rifleman 目标先设为 6，后改为 10。
- light_tank 目标设为 2，但长期处于等待资源或缺少有效产能的状态。

军事方面，模型没有调用 `launch_assault`，而是多次调用即时 `attack_move_unit`，主要把若干 rifleman 推到 `(35,48)`、`(40,48)`、`(30,48)`、`(28,48)` 等仍靠近己方一侧的位置。后期部分调用使用了已经死亡的 unit ID，返回 `invalid_unit`；模型仍未转为全军持续进攻。

该样本说明：简单高层工具至少解决了“持续生产”这一局部问题，但没有让模型形成或选择全军进攻。819 ticks 比实验 A 的 346 ticks 更长，不能据一局随机对局直接归因于改动；重要事实是行为结构发生了部分变化，而胜利目标仍未取得任何进展。

单元测试已经证明 `launch_assault` 的服务端机制能在达到兵力阈值后发出命令，并吸纳注册后新出现的单位；但它尚未在真实 LLM benchmark 中被模型调用，因此不能据单元测试声称它改善了 LLM 战略表现。

## 9. 已经可以确认的事实

1. 不是“LLM 完全不会调用工具”。它每局有大量读取和动作调用。
2. 不是“LLM 不知道敌方位置”。当前无战争迷雾，读取工具提供全图敌方实体；system prompt 也给出双方 HQ 坐标。
3. 不是“一个 turn 不能多次使用工具”。系统明确支持，并且实际记录中同一 turn 内工具结果对应不断推进的 tick。
4. 不是“缺少持续执行机制”。原通用 Mission 和当前参数化战略都能跨 tick 执行。
5. 通用 plan 的复杂 schema 确实降低了使用吸引力，但它不是全部问题：将持续生产简化后模型采用了，将全军进攻同样简化后模型仍未采用。
6. random CPU 并非具备深度推理；它的优势来自少量稳定规则持续覆盖所有新单位，并始终把战斗力导向敌方基地和建筑。
7. 当前 LLM 的局部行动很多，但五局基线加两局实验中都没有对敌方 HQ 造成伤害。

## 10. 尚不能确认、请勿当作结论的假设

以下解释目前都没有被充分实验区分：

- 模型是否缺少长程战略推理能力，还是工具描述/命名没有触发已有能力。
- 模型是否把“安全集结”和“继续发展经济”赋予了过高价值。
- 模型是否因为即时动作反馈更直接而系统性偏好底层工具。
- 模型是否误解 attack-move、地图尺度、胜利条件或战斗力门槛。
- 模型是否形成了战略但无法在 transcript=false 的记录中观察到。
- CPU 的零模型延迟和高频重新下令对结果贡献有多大。
- 当前 system prompt 的信息密度、工具数量或上下文裁剪是否削弱了战略信息。
- 更换模型后问题是否显著缓解；当前主要失败样本集中在一个模型/preset。
- 如果强制模型先调用一个战略工具，它会做出合理战略，还是只会形式化填写参数后继续局部操作。

我们之前曾把某些假设过早表述为“真正根因”，但后续 benchmark 没有支持这种确定性。本文不再把它们包装成结论。

## 11. 当前记录与观测限制

- 七局关键记录均为 evaluation profile。
- `includeTranscript=false`，所以没有完整 system message、assistant 自然语言输出和逐请求消息正文。
- 有 model request 数量、tool calls、参数、工具结果、命令、command provenance、tick delta、胜负和部分 latency 指标。
- 因此可以准确说“模型调用了什么、游戏发生了什么”，但不能准确说“模型为什么这么想”。
- 原始五局不是大样本统计，只能证明当前组合存在稳定且严重的失败，不能精确估计总体胜率。
- random CPU 每局路径和选择不同；跨单局比较终局 tick 不能直接视为某项改动的因果效果。

## 12. 我们希望专家重点回答的问题

### 12.1 问题定位

1. 从上述行为看，最可能是模型能力问题、agent 接口问题、控制层抽象问题、实时调度问题，还是 benchmark 设计混合了多个因素？
2. 还缺哪些关键证据，才能区分“没有形成战略”“形成了但没执行”“工具选择失败”“执行层失败”？
3. 下一批 Match Record 应打开或增加哪些最小观测字段？是否必须启用完整 transcript？

### 12.2 接口设计

4. 面向 RTS 的 LLM 工具应该暴露单位级动作、兵团级动作、目标/政策级动作，还是分层组合？边界应如何划分？
5. 高层工具应由模型主动选择，还是控制器应把所有新单位默认纳入一个可修改 doctrine？如果默认纳入，如何避免把战略硬编码进环境？
6. 如何让模型表达“赢法”和阶段转换，而不重新发明一个难写的 workflow DSL？
7. 是否应该保留即时 `attack_move_unit` 作为例外工具？如果保留，怎样避免它取代持续战略？单纯隐藏或禁用它能证明什么、又不能证明什么？

### 12.3 实验设计

8. 最小、信息增益最高的 ablation 顺序是什么？例如：强制一次 `launch_assault`、隐藏部分即时工具、固定初始经济/军队、离线给定同一快照、不同模型横向测试、CPU 降频等。
9. 应如何设计一个不依赖最终胜负的战略能力评测？候选指标包括首次伤害敌方建筑、战斗单位获得进攻目标的覆盖率、出生到首次有效命令延迟、已投资战斗力转化为建筑伤害的比例等。
10. 如何把模型网络延迟/调用吞吐与战略质量分离，同时保留真实实时环境？

### 12.4 可执行建议

11. 如果只能做一项最小改动来验证最关键假设，应该改什么，预期观察到什么，什么结果会证伪该假设？
12. 如果需要重构，请给出清晰的输入、输出、状态所有权和验收标准，而不是只建议“增加规划”“加入 memory”或“写更强 prompt”。

## 13. 我们不希望评审建立在这些误解上

- 不要把“一个 turn 覆盖整局”直接判定为架构错误；这是标准多轮 tool loop 的刻意设计。
- 不要把 random CPU 理解成每一步均匀随机；它有随机宏观选择，也有稳定执行规则。
- 不要因为 CPU 工具调用更多，就直接把全部失败归因于调用数量；LLM 的核心异常是没有把已生产战斗力转化成任何敌方 HQ 伤害。
- 不要假设通用 plan 不存在；它存在且可执行，只是模型很少有效使用。
- 不要假设把 plan 参数简化就已经解决问题；持续生产被采用，全军进攻没有被采用。
- 不要从 transcript=false 的记录虚构模型内心推理。
- 不要把单局持续时间变化当成因果结论。
